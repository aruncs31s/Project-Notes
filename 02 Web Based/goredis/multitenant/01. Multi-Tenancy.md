# 01. Multi-Tenancy

This guide covers the architecture, implementation, and usage of the multi-tenant cache client in the `goredis` library.

---

## 🏢 Multi-Tenant Client Architecture

In enterprise applications, data isolation between different tenants (e.g., companies, users) is a strict requirement. The `MultiTenantClient` (defined in [multitenant.go](file:///home/aruncs/Projects/Mine/goredis/multitenant.go)) addresses this by providing namespace-based cache isolation for each tenant while reusing the same underlying Redis connection pool.

```
                  ┌──────────────────────┐
                  │  MultiTenantClient   │
                  └──────────┬───────────┘
                             │
                             ├───────────────┐
                             ▼               ▼
                       Tenant "org_A"  Tenant "org_B"
                     ┌───────────────┐┌───────────────┐
                     │ Client Wrapper││ Client Wrapper│
                     │Prefix: prod:A ││Prefix: prod:B │
                     └───────┬───────┘└───────┬───────┘
                             │                │
                             └───────┬────────┘
                                     ▼
                      ┌──────────────────────────────┐
                      │ Shared Redis Connection Pool │
                      └──────────────────────────────┘
```

## 🔒 Namespace Isolation & Thread Safety

### 1. Key Isolation Prefix
Each tenant's cache client is lazily created and configured with a custom namespace:
```
Namespace = <base> + ":" + <tenantID>
```
For example, if the environment base is `"prod"` and a request comes in for tenant `"org_123"`, the namespace is `"prod:org_123"`. All keys and tags generated for this tenant will be isolated automatically (e.g., `prod:org_123:user:42` and `prod:org_123:tag:users`).

### 2. Thread-Safe Lazy Initialization
`MultiTenantClient` uses a read-write lock (`sync.RWMutex`) and a double-checked locking pattern in its `Tenant` method to ensure thread safety during lazy client initialization without introducing lock contention:

```go
func (m *MultiTenantClient) Tenant(tenantID string) *Client {
	m.mu.RLock()
	c, ok := m.clients[tenantID]
	m.mu.RUnlock()
	if ok {
		return c
	}

	m.mu.Lock()
	defer m.mu.Unlock()

	// Double-check after acquiring write lock
	if c, ok := m.clients[tenantID]; ok {
		return c
	}

	ns := m.base + ":" + tenantID
	c = New(m.rdb, append(m.opts, WithNamespace(ns))...)
	m.clients[tenantID] = c
	return c
}
```

## ⚡ Multi-Tenant Usage Example

The library exposes generic wrapper functions (ending with `T`) that take the `MultiTenantClient` and the `tenantID` to run operations on a specific tenant's cache.

```go
package main

import (
	"context"
	"fmt"
	"time"

	"github.com/aruncs31s/goredis"
	"github.com/go-redis/redis/v8"
)

type Organization struct {
	Name string `json:"name"`
}

func main() {
	rdb := redis.NewClient(&redis.Options{Addr: "localhost:6379"})
	
	// Create the multi-tenant manager
	// "prod" is the base namespace
	mtClient := goredis.NewMultiTenant(rdb, "prod")
	ctx := context.Background()

	// 1. Fetch data for Tenant "org_A"
	// Key will be cached under: "prod:org_A:settings"
	orgA, err := goredis.CacheGetOrFetchT(ctx, mtClient, "org_A", "settings", 5*time.Minute,
		func() (*Organization, error) {
			return &Organization{Name: "Org A Corp"}, nil
		},
		"config",
	)
	if err == nil {
		fmt.Printf("Tenant A Name: %s\n", orgA.Name)
	}

	// 2. Fetch data for Tenant "org_B"
	// Key will be cached under: "prod:org_B:settings"
	orgB, err := goredis.CacheGetOrFetchT(ctx, mtClient, "org_B", "settings", 5*time.Minute,
		func() (*Organization, error) {
			return &Organization{Name: "Org B Ltd"}, nil
		},
		"config",
	)
	if err == nil {
		fmt.Printf("Tenant B Name: %s\n", orgB.Name)
	}

	// 3. Invalidate tag for Tenant A only
	// Tenant B's cache entries remain completely untouched!
	err = mtClient.InvalidateByTags(ctx, "org_A", "config")
	if err != nil {
		panic(err)
	}
}
```

> [!TIP]
> Options passed to `NewMultiTenant` (like codecs, metrics logger, etc.) are automatically shared across all created tenant clients.
